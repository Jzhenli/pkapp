## 1. 定位与总纲

- 混淆/加密体系在 pkapp 中的职责是**抬高逆向成本**，机密性底线是 K 体系（pk_x1/pk_x2 AES-GCM + AAD）。
- 图灵机层面的边界先说死：**不存在"能运行但不能被逆向"的程序**——明文逻辑必然出现在内存。安全工程的交付物不是"防住"，是**攻击成本 > 攻击收益的成本曲线**。
- ★R-3★ 总体定位表述（收敛后）：走完本路线后，**BCC 覆盖的那几个函数达到原生逆向成本**，**应用整体达到"商用级混淆"**（私有实现符号清零 + 密文封装 + K 隔离）——不宣称"整体到达行业均衡点"。K 恢复 / runtime dump（攻击树 1A）仍是残余入口，需要 deferred 的档位 3（白盒）/ 4（硬件证明）才能关闭。

### 1.1 防线分工（不互相替代，成本相乘）

| 防线 | 防的对象 | 失守后的剩余价值 |
|---|---|---|
| K 体系（加密） | 批量解密 / 二次分发 | — |
| K 派生（档位 1） | **横向通吃**（提一次 K 破所有应用） | 单应用纵向提取仍可行 |
| 混淆（RFT/mix-str） | 解密后代码的**理解成本** | K 泄露时唯一还站着的防线 |
| BCC（Cython 引擎） | 覆盖面内函数的**逆向形态**（字节码 → 机器码） | — |
| 纵深（自检/反调试/生命周期） | 运行时 patch / 内存 dump | — |

逆向的实际流程是串联的：提 K → 解 blob → 读代码 → 二次利用。任何一环加强，整链成本相乘而非取最小。

### 1.2 攻击树速览（与设计稿 §9 对齐）

- **1A 动态**：frida/调试器 attach → hook pk_x2 直接 dump 明文——**未关闭**（残余风险，§6 明示）；
- **1B 静态离线**：IDA 提取 K → 自写解密器批量解 blob——被档位 1 压制为"每包一破"；
- 3.12 反编译工具链窗口会随版本演进贬值，需周期重评估（设计稿 §9.4）。

## 2. 现状基线（实读结论，2026-10）

- `pkapp/packager/obfuscate.py`（782 行）：symtable 驱动的 AST 变换。
  - 改名面 = **仅 function scope 的非参数局部绑定**（模块级/类体/参数名全豁免）——实测 app/ 树改名 56 个局部符号，43 个模块级函数名与全部参数名保持原样（"低质量 RFT"定性的由来）。
  - 字符串加密（期 2 S5/S6）**已完整落地**：确定性 keystream（SHA256 流）+ XOR + 惰性解密 stub（key32 自裹派生，无字面量）+ 禁换集两遍设计。质量高于"简陋"的预期，差距只在覆盖面。
- keylib：K 以分散+XOR 偏置形态**静态烧在件内**，全局一把 K 分发所有应用——IDA 跟踪 pk_x2 的 key 引用即可恢复（"可恢复混淆"，防横向不防纵向）。
- 威胁模型现状：逆向者一次投入（逆向 keylib 或直接加载调 pk_x2），**通吃所有 pkapp 应用的所有 blob**——这是当前链条最薄的一环。

## 3. 档位 1：K 派生化（per-app 烧件）

### 3.1 核心思想

keylib 从"通用件内置一把 K"改为"**每次打包现场派生 K_app、编译期烧进本包专属的 keylib 副本**"。K_master 永不出构建机。

```
K_master（构建机秘密：PKAPP_MASTER_KEY，永不入包/入库）
    │  HKDF-SHA256(salt, info = app_id)
    ▼
K_app（per-app；salt 策略见 §3.2）
    │  编译期注入（生成 kdata.c 链接，非二进制 patch）
    ▼
pk_x1/pk_x2/pk_x4 照常使用（blob 格式零变化）
key_id = f(K_app) → manifest code_key_id（现有配对链零变化）
```

### 3.2 salt 策略与 G5 兼容（★R-2★ P0 修订）

v1.0 的 per-app × per-build salt 设计**推翻了 G5 的跨构建稳定前提**：同一份源码两次构建 → K_app 不同 → 密文不同 → app_hash 必变 → 指纹缓存跨构建失效。修订为**隔离强度可选，G5 默认不破**：

- **默认档（salt = 常量/不启用）**：K_app = HKDF(K_master, info=app_id)——同 app_id 恒同 K。G5 的"密文稳定 → app_hash 跨构建不变"**完整保留**；横向隔离达成（每 app 一把 K，不跨应用迁移）。
- **per-build 档（显式开启）**：salt = 随机 per-build，写入 manifest——同源码两次构建密文不同。适用于"单应用自身也需防批量比对"的高危场景。**开启即声明放弃跨构建指纹复用**（manifest 标记，构建工具据此跳过指纹断言）。
- **app_hash 解耦修正（两档通用）**：app_hash 的哈希输入从**密文改为明文 marshal**（PYTHONHASHSEED=0 代编，明文 marshal 天然确定性）——指纹语义与 K 彻底解耦，per-build 档下指纹缓存仍可工作（同明文 → 同指纹，运行期解包缓存命中不失效）。blob 密文仍按所选档位派生。
  - 实施时核对设计稿 G5/app_hash 的全部消费点（指纹缓存、更新对比、CI 断言），确保换输入后语义等价。

**诚实边界**：单个目标的纵向提取成本（IDA 跟 pk_x2 拿 K）不变——那是档位 3（白盒密码学）的领域。防"每设备类一破"需硬件证明/在线激活（档位 4，独立评估）。

### 3.3 架构改动面与运维面迁移（★R-7★ P2 修订）

**代码改动（5 处）**：
1. **keylib/src/key.c**：K 存储区从源码常量改为构建期生成的独立编译单元（`kdata.c`）；pk_x1/x2/x3/x4 逻辑零改动。
2. **pkapp/packager/keylib.py**：`derive_k_app`（HKDF，纯 stdlib）+ `generate_kdata_c`（分散形态生成器）。
3. **package 管线**：`_stage_keylib` 从"定位预制件/锚点 patch"改为"现场定制编译"。
4. **manifest / _codekey / 壳**：零改动（code_key_id 配对、blob 格式、pk_x4 契约原样）。
5. **测试**：隔离对拍（A 包 keylib 解 B 包 blob 必失败）、G5 确定性（默认档）、app_hash 解耦对拍、三平台编译矩阵冒烟、全量回归。

**运维面迁移（v1.0 低估，如实列出）**：
- package 步骤从"复用预制件 + 锚点 patch"变为"**触发 C 编译**"——打包机需要可用工具链（Windows 包 = MSVC、Android 包 = NDK、Linux 包 = clang/gcc，各自目标平台各编一次，非全矩阵）；build 时长增加秒级~十秒级，CI 缓存可摊薄；
- **新信任根进入运维**：K_master 的生成、分发、轮换、构建机准入要成文（准入流程并入 doctor 检查 + 文档）；此前构建机只持有工具链与签名材料，现在多一把"未来所有包的根密钥"——泄露影响面 = 未来所有包（已发布包自持不受影响；丢失无灾难，换 master 照常出货）；
- 预制件分发模式（_vendor/keylib）退化为 fallback 或退役——打包机离线场景需保留预制编译路径或明确放弃。

### 3.4 迁移兼容性

- blob 格式 / AAD / key_id 机制不变，下游零迁移。
- 新旧包天然不互认（K 不同 → key_id 配对 / -4 AUTH 拦截）——keylib 随包整体分发，无跨包混装场景。

## 4. 混淆层强化：P1（RFT 高质量版）+ P1.5（mix-str 扩面）

### 4.1 P1-RFT：跨模块统一改名（★R-4★ 验收线修订）

**范围（第一版）**：模块级 def/class + 顶层变量 + 跨模块引用同步（`a.foo` 属性改写、`from a import foo as f` 的 alias.name 改写、绑定名 asname 保留）。

**红线（第一版绝不触碰）**：类体方法/属性名（pydantic 字段、`self.x`、dataclass、ORM）；参数名（FastAPI DI / keyword 公开面）；模块名本身（_EncFinder 按 import 名认领——G6 链硬前提）；entry/框架面（`app = FastAPI()`、`__main__`、bootstrap 拾取面 → protected 集从 appspec 派生）。

**验收线（★R-4★ 精确表述）**：
> **私有实现符号清零，公开契约与数据形状仍可读。**

对一个 FastAPI 应用，RFT 后攻击者**仍能完整读出**：pydantic schema 字段、路由签名与参数名、公开 API 名、类名——这是主动取舍（藏的是私有实现，不是数据形状；数据形状本来就在 API 契约里公开）。验收用逆向演练核对的是：私有函数名、内部流程符号、内部状态名清零。**评审验收时按此口径，不按"所有名字消失"。**

**高危点与防线（全部有明确实现路径）**：

| # | 坑 | 防线 | 可锁死 |
|---|---|---|---|
| 1 | 动态字符串引用（getattr/hasattr/dict 键） | 第一遍收集后对将改名符号扫全树 Constant 精确匹配 → 命中即豁免（保守上界） | ✅ |
| 2 | entry/框架面 | protected 集从 appspec 派生；模块名永不改 | ✅ |
| 3 | 跨模块引用改写断裂 | import 图两遍：收集 → 同步改写 | ✅（对拍是生命线） |
| 4 | keyword 一致性 | 映射表驱动天然同改；外部调用面参数名豁免不动 | ✅ |
| 5 | G5 确定性 | 沿用确定序（symtable 返回序 + counter，禁 set 迭代序）；跨模块按文件序 | ✅ |
| 6 | traceback 可读性 | 映射表不落盘（落盘=改名归零）；开发者自担排障成本 | 已知取舍 |

**测试防线（测试先行，先于实现写）**：
1. import 图对拍（定义点与全部引用点同新名）；
2. 串匹配豁免点名测试（构造 getattr 场景验证不破）；
3. 端到端混淆冒烟（混淆产物打 demo 包 → 启动 → healthz/登录断言）——先确认 test_package/test_real_runtime 覆盖度，缺则补；
4. G5 确定性断言扩到跨模块 stats。

### 4.1.5 自研质量保证机制（★R-10★：回答"凭什么信自研质量"）

核心思想：**正确性不靠"开发者写对"，靠"每次构建机器验证"**——改名前后的语义等价性可工程验证。五个机制：

**① 双编译对拍——全量断言，非抽样测试**
每模块每构建：改名前后 code object 的符号面（`co_names`/`co_varnames`/const 池字符串）差异集合必须与映射表作用域逐项对应——多改、少改、错改任何一个，对拍当场炸。测试是抽样，对拍是全量：任何一次改名错误都到不了打包。方法论同源：期 1/2 的双端常量对拍、防线 A/B。

**★R-12★ ① 边界一 + 落地前置（实证校正）**：
- *边界一*：全量对拍验证「改名范围 = 映射表」，证明不了「程序仍正确」。漏改（保守豁免吞掉的动态 construct）只损覆盖率不炸；真正运行时崩的 case 仍靠 ③ 真实项目矩阵 + §4.1 测试#3 端到端冒烟兜底。四机制分层，**① 不替代运行时门禁**——评审口径须明确此点，避免误读「有对拍即够」。
- *落地前置（已读 `obfuscate.py` 实证）*：现状 `transform()` 是**逐模块、局部计数器**（`counter=[0]` 每次调用重置，line 755），改名面**仅 function-local 非参数绑定**（低质量 RFT 基线）；**跨模块 `a.foo` 属性改写 / import alias 同步均未实现**（`_lookup` 在 module 层直接返回 None，docstring 明示 Attribute 天然不碰）。故 R-10 ① 的「全局映射对拍」**不能直接落地于现状**——须先由 P1-RFT 完成：(i) per-file 局部计数器升级为**跨模块全局映射（key=(module,name)，全局唯一计数器）**；(ii) import 图两遍（收集→同步改写）+ `a.foo` 属性改写。全局对拍依赖这张全局映射为前置，否则跨模块漏改无对象可查。

**★R-13★ ① 边界二（复合变换对拍）**：对拍对象须是 **RFT + mix-str 复合变换后**的符号面，非只改名。const 池变化同时来自字符串加密（期 2 keystream XOR），对拍须同时比对「改名映射表 + 字符串密钥表」两张表，否则字符串加密引入的 const 变化会被误判「错改」。

**② 保守性设计——失败模式非对称，宁漏改不错改**
漏改（该改没改）= 覆盖率损失，可接受；错改（不该改的改了）= 运行时炸/行为改变，灾难。铁律：**拿不准一律豁免**。每条豁免主动宣布（reason code 进构建日志），不是"忘了改"——覆盖率损失可见、可控、可后续收敛。

**③ 通用性 = 边界声明 + 矩阵锁死，不靠"支持一切"**
- **语言特性矩阵**：Python 语法特性（闭包/装饰器/生成器/async/继承链/描述符/walrus/match/注解……）× 改名组合 → 行为断言用例；一次建设，新语法版本加行。"通用"的实质 = 实测过的特性清单逐版扩张；
- **真实项目矩阵**：内部项目 + 2-3 个形态各异 demo（纯 API/带 ORM/带后台任务）进回归树；
- 封闭世界边界：第三方库符号不进映射表，需覆盖的面只有 app 树；
- 明确不支持声明：运行时自改代码/重度 metaclass 魔法 → 排除面检测即整模块跳过（fail-soft），不假装支持。

**④ 覆盖率与确定性常驻可度量**
映射表确定序 → 同输入同输出（G5 延伸）；构建日志常驻改名统计（改了多少/豁免多少/各因何种 reason code）——"43→0"从一次性演练变成每次构建的可见字段，覆盖率回退会被看见而不是被埋。

**⑤ 渐进路径——质量是运营出来的**
第一版范围 + 全部防线 → demo 树 → 真实项目矩阵跑一个版本周期 → 边缘 case 沉淀为矩阵新行与豁免新规则，覆盖率与信心同步增长。不存在"一次设计出终极通用 RFT"；PyArmor RFT 同样是社区撞坑多年打磨的产物——区别只是他们用付费用户撞，我们用项目矩阵撞，撞出的每一条都沉淀进测试。

**结论**：自研 RFT 的"难"不在算法（AST 改名是成熟技术域），在质量体系纪律——对拍闸、保守豁免、矩阵回归、可度量覆盖率，四样缺一即玩具。四样全是 pkapp 已验证方法论的第二应用场景，非第一份建设。

### 4.2 P1.5-mix-str：覆盖面扩两项，降级执行

- ① JoinedStr（f-string）常量段放开——收益低（多为日志文案），后置；② `_MIN_STR` 16→8（forbidden 机制已防同串断裂）——随 P1 顺手做 ✅（落地含伴生对拍规则：全常量键 dict 任一键被加密后 3.12 由 BUILD_CONST_KEY_MAP 退化 BUILD_MAP，键元组消失/未加密键散现，verify_parity 按「键元组逐元素 ∈ str_table ∪ 新现散串」全命中放行）。技术上无不可落地项，性价比低于 RFT，不单独立项。

## 5. P2：Cython 引擎 BCC（★未来方案★——本轮不实施，启动前置见 §7）

> ★R-11★ 定位调整：为快速落地，BCC 整体列为未来方案。顺序上无牺牲——RFT 是 BCC 的前置硬顺序（★R-8★），P1 落地即 P2 的必要前提；且档位 1 + P1 已覆盖最大威胁面（O(1)→O(n) 通吃 + 私有符号清零），BCC 的增量（局部 native 化）可后置。本章设计内容保留作为启动时的方案基础，评审仅对其定位拍板，不拍板其内部细节。

### 5.1 三分法判定（评审确认的结论）

| 路线 | 判定 |
|---|---|
| (i) 手工把核心算法写成 C/C++ .pyd | 只对小且稳定核心可行；本质是原生代码不是混淆工具；覆盖面对不起"BCC 全部核心" |
| (ii) 自研字节码→C 转译器 | 研究级工程量（动态类型/异常/生成器/闭包/内省/async）；脆弱、维护黑洞；**否决** |
| **(iii) Cython 当 BCC 引擎，自研只做编排** | **采纳**——正确性与韧性来自成熟编译器，pkapp 只挑哪些核心进 BCC |

### 5.2 选型：Cython（非 Nuitka）+ non-goal 修订（★R-5★ P1 修订）

- **架构理由**：Nuitka 本体是全程序编译器（onefile/standalone 自成体系），与 pkapp 的"运行期壳 + site-packages + spk 解包 + 壳协议"两套世界观，缝合成本高；Cython 是**模块级**编译器，产物 = 普通扩展模块（`lib<mod>.cpython-312.so` / `<mod>.pyd`）；混编生态成熟；三平台编译矩阵工具链现成。
- **non-goal 修订（需评审拍板）**：设计稿原 non-goal"无新依赖（密码学在原生件内）"与 Cython 引入直接冲突——**用"新增编译器工具链依赖（Cython + 三平台编译矩阵 + 版本匹配跟踪）"换"核心逻辑 native 化"是本路线最重的 trade-off**。设计稿 §3 对 Nuitka 的否决理由之一（新依赖/构建变慢）对 Cython 同样成立，区别只在 Cython 的产物形态与 pkapp 分发链契合使成本可控。**此 trade-off 必须显式拍板接受，评审不通过则 P2 整体搁置。**

### 5.3 BCC 模块的 loader 改造（★R-1★ P0 新增——v1.0 最大遗漏）

**问题**：`app` 是 _EncFinder 产出的**虚拟包**（无真实 `__path__`），BCC 产物不走 blob。`import app._gate_compiled` 时：_EncFinder 按 mid 查 index → 查不到（已排除 blob）→ None；PathFinder 无 `__path__` 可搜 → 死路。**"扩展件分发链现成通道"的 v1.0 表述不成立**——keylib 通道是"单件固定位置"，BCC 模块是挂在虚拟包下的多件动态名，这是 loader 层真实改造。

**采纳方案：_EncFinder 对 BCC 条目特判产出扩展模块 spec**（保持 `app.*` 命名空间与虚拟包结构不变）：

1. **index 格式扩展**：index.enc 增加 BCC 条目行（如 `B app._gate_compiled`，与现有 `M `行并列；`R `资源预留位模式复用）——index 本身密文，BCC 清单不泄露。
2. **find_spec 特判**：_EncFinder 命中 `B `条目时，不返回 blob loader，返回 `importlib.machinery.ExtensionFileLoader(fullname, <真实落盘路径>)` 的 spec（origin = 落盘路径，供 traceback）。
3. **落盘位置规则**（复用 _dll_path 既有分派逻辑）：
   - Android：`nativeLibraryDir/lib<basename>.cpython-312.so`（apk.py 把 BCC 产物按 lib 前缀命名拷入 jniLibs——与 55 个既有扩展件同一通道，NdkExtFinder 不参与，因子模块 import 由 _EncFinder 认领）；
   - Windows：`sys.executable` 旁 `<mod>.pyd`（exe 旁分发点，keylib 同位）；
   - Linux：runtime 目录（manifest 旁）。
4. **构建链联动**：assemble 期 BCC 模块从加密树排除（不进 blob / index 记 `B `行）→ 产物进扩展件分发通道（spk 内新分区或 jniLibs 直拷，实施时按现有扩展件通道接入）。
5. **失败语义**：B 条目对应 .pyd 缺失/架构不符 → ExtensionFileLoader 抛 ImportError → 现有错误页中性文案路径（fail-closed 与 blob 缺失同构）。
6. **测试**：虚拟包子模块 import 对拍（`app._gate_compiled` 可导入且 `app.__path__` 语义不变）、缺件 fail-closed、B/M 条目混排 index 解析。

### 5.4 编排层设计

```
标记：appspec 配置可 BCC 模块/函数
  → RFT 必须先行（统一改名 + 字符串加密 + 剥 docstring）★R-8★
  → BCC 模块：RFT 后 AST → ast.unparse 临时源 → cythonize（产物 = 扩展模块）
  → 三平台编译（keylib 同款矩阵）
  → 扩展件分发通道 + index 记 B 行（§5.3）→ 弃源码（G6）
```

**RFT 先行是硬顺序（★R-8★）**：Cython 自身不做任何符号混淆——所有 Python 级名字会 intern 成字符串常量埋进二进制（`__pyx_n_s_*` 表、PyMethodDef 方法表），未过 RFT 的 BCC 产物 `strings` 一扫即得完整符号表，伪 C 反编译配合下语义还原成本反而低于混淆后的字节码（BCC 等于白做一半）。RFT 前置后，二进制中仅剩混淆名 + 已加密字符串（解密 stub 为合法 Python，随模块编译成 C，运行期解密）。两个工程要点：① cythonize 只吃源码文本，BCC 模块走 `ast.unparse` 临时源环节，语义保真纳入对拍；② BCC 模块**不进豁免清单**、走统一映射——跨模块映射表保证未编译侧 import 点与 .pyd 导出名同新名，一致性问题天然消解；公开契约参数名由 §4.1 红线（参数名不动）自然覆盖，口径自洽。

**选择策略三层（★R-9★ 通用性修订——不做人工挑选）**：
1. **默认关闭**：BCC 是 appspec opt-in 特性（同 code_encryption 模式）——三平台编译矩阵有构建环境门槛（MSVC/NDK），默认开启会使多数用户构建失败；
2. **启用后自动筛选，零人工**：复用 RFT 的 AST/symtable 收集器静态扫描——含 dataclass 定义、`exec/eval/getsource`、路由装饰器、pydantic 模型、动态 import 面的模块**自动排除**；其余**全部 cythonize**（用"能编的全编"回避"pkapp 无法判定业务敏感面"的不可通用问题，保护最大化）；个别模块编译失败**自动回退 RFT+pyc**，构建不炸、日志留痕；
3. **appspec include/exclude 仅高级覆盖**（编译时长/已知兼容微调），非必填。

**粒度澄清（★R-9★）**：BCC 单位是**模块**，不是函数（Cython 模块级编译器，函数级拆编不进生产管线）。"试点 2-3 个函数"的准确含义 = 将其收敛进可独立编译的模块；模块内混路由/dataclass → 整模块自动回退，不存在模块内部分函数编译。

**排除面合同（三条全满足才进 BCC，静态可检测子集由自动筛选执行）**：不含 dataclass 定义/运行时 exec/code hack/依赖 getsource 的内省；不碰框架对象生命周期（FastAPI 请求对象等厚 PyObject 语义）、无复杂异常流；安全敏感且体积可控（鉴权校验、握手验证、token 派生）。试点从 `_gate` 鉴权链的独立模块起步。

**覆盖面表述（★R-3★ 收敛）**：BCC 只让**覆盖面内的函数**达到原生逆向成本；应用整体仍是"字节码级混淆 + 局部原生"——任何对外表述按此收敛，不得宣称"核心逻辑全部 native 化"。

**★R-14★ P2 启动收口硬约束（N2 / N3 收口，未来方案不阻塞当前）**：
- **N2 回退口径锁死**：§5.4 自动筛选「个别模块编译失败自动回退 RFT+pyc」——回退产物**必须 = RFT + 加密 blob（走现有 _EncFinder 加密树通道），严禁落明文 .pyc**（明文 pyc 直接击穿 G1）。P2 启动时把此句改写为硬约束。
- **N3 口径二选一**：§5.4 R-9「能编的全编」会让 BCC 覆盖面远超 §1 ★R-3★「局部原生」口径（§5.4 覆盖面表述同）。P2 启动时二选一：要么把 R-3 口径改为「多数模块 native」，要么把 R-9 收敛回「仅安全敏感且体积可控的模块」（与 §5.4 排除面合同一致）。两处口径须对齐，避免对外表述自相矛盾。

### 5.5 风险清单

## 6. 纵深层与残余风险（★R-6★ P2 修订：明示"承认而非解决"）

**问题定性**：自研 keylib + 引导装载链 + _EncFinder 没有经过 PyArmor runtime 级的攻击打磨，是头号目标。

| 项 | 内容 | 定级 |
|---|---|---|
| keylib 完整性自检 | 关键段 checksum 自校验，patch 即拒 | 缓解（设计稿 §5.4⑤ 曾主动 deferred：真攻击者 patch 后顺手修校验和，边际低——维持 deferred 判断，列为可选增强） |
| K 内存生命周期 | 首次解密展开、用完清零 | 缓解 |
| 引导链审计 | pk_x4/fail-closed 路径复核 | 审计项 |

**残余风险（明示，勿误读为已关闭）**：
- **1A 动态路线未关闭**：攻击者 patch 单点（或 hook pk_x2）→ dump 明文。Windows keylib dll 无签名（设计稿 §9.3④）降低了 patch 门槛。三步路线走完后此入口仍在，只是其成果**不可迁移**（档位 1）且解出后仍面对混淆（P1）。
- §6 的三项缓解抬高的是"随手 patch"门槛，**不针对有能力修复校验和的攻击者**。对本项目威胁模型（挡随手扒/魔改，不挡国家级/专职逆向）此残余可接受——评审确认该威胁档位即可。
